# Investigation protocol

## Unit of work: a target-to-workflow record

A target is an observable feature in an identifiable reference, not simply a game title or aesthetic label. Example: independently rotating textured architectural components remain legible behind orthogonally projected bullets. First define what would count as an acceptable result and what is not required.

1. Register the target: title/platform/version, timestamp or scene, observation, desired property, negative/control example, intended application.
2. Acquire evidence: original production accounts; professional transferable instruction; independent/homelab reconstruction; technical specifications and open implementations; direct observation. Record contradictory evidence.
3. Decompose: distinguish art construction, animation, render operations, camera, compositing, interaction and sound when relevant.
4. Propose one or more recipes: tools/versions, inputs, transformations, outputs, budgets, manual steps, alternatives and failure modes.
5. Run a small original specimen. Retain source, exports, screenshots/video if rights permit, test steps, timings and reproducible parameters. Vary one constraint at a time where practical.
6. Compare under matched viewing conditions: native and final display, representative motion, clutter, lighting or input conditions. Record both operational correctness and perceived quality. Compare at least one simpler alternative when deciding to add complexity.
7. Generalize if needed; decide promote, revise, reject, defer or stop. Register the actual evidence and remaining uncertainty.

## Illustration-derived asset prerequisite

For illustration-derived targets, register acquisition/source status and rights; choose character-to-viewport and world-to-raster scale at the intended camera; test anatomy, resolution and repeated poses before locking source and export dimensions. Distinguish visible frame bounds, art workspace, animation registration, atlas packing and display scale. Specify identity-bearing details, permitted adaptation, layer responsibilities, editable deliverables and revision checkpoints; test both art-to-runtime and revision-to-runtime handoff. See [G02-P01](../research/studies/G02-P01.md). A found illustration is reference evidence, not intrinsically a production asset.

## Evidence kinds (not ranked solely by prestige)

A: documented original production method; B: transferable professional method; C: inference or independent reconstruction of an observable result; D: our independently tested method. An independent account can provide stronger operational evidence than a studio interview. Several kinds may support the same recipe. These are separate from R0–R5 maturity.

For new or materially revised records, write evidence-kind labels **EK-A/EK-B/EK-C/EK-D** to distinguish them from charter terminal conditions **TC-A/TC-B/TC-C**. These are aliases for the original A–D evidence kinds and A/B/C terminal conditions, not changes of criteria; older records retain original language. R0–R5 remains maturity per specified record and claim. A separate semantic/reception ladder in [G06](EFFECTS_SEMIOTICS.md) is optionally written **SEM-S0…SEM-S4**; it is not a replacement for maturity or viewer evidence. No numerical aggregation across scales.

Independent researchers, homebrew developers, technical doujin authors, artists' notebooks and toolmakers are first-class sources. Prefer their runnable code, editable projects, parameters and documented failures over appearance-only showcases, while checking licensing and version compatibility.

## Evaluation dimensions

Fidelity to declared properties; expressivity; controllability; manual effort; runtime/memory cost; reusability; composability; maintainability; independence; legibility and accessibility where applicable. Record criteria and thresholds per target before testing. Not all need numerical scores, and no aggregate score substitutes for a failed essential requirement.

## Evaluation lanes and experienced-quality intentions (2026-11-18 clarification)

When relevant, record **intended experiential quality** (e.g. force, readability, elation, apprehension) separately from observed response, and inspect the output in its **representative camera/background/action/audio context** and final display scale. Differentiate (1) technical contract checks, (2) situated artistic or author critique, (3) actual viewer response under a stated procedure *if any*, and (4) authoring/production readiness including editable source, revision and import. Success in one lane does not prove another. Creator testimony establishes intent, not audience efficacy. Do not require audience testing to close a bounded craft question unless reception is itself the claim. See [G06 effects standard](EFFECTS_STANDARD.md); the common target-to-workflow unit and terminal conditions remain unchanged for all domains.

## Minimum record schema

    ID / title / domain(s) / status / R-level
    Target and intended use
    Source IDs / verification / rights / evidence kinds
    Observable properties vs inferred mechanism
    Candidate recipes and alternatives
    Environment / exact versions / budgets
    Original test assets / commands / expected output
    Acceptance checks / results / negative results
    Transfer test / integration dependencies
    Decision / limitations / next bounded question

## Search policy

For proportional and illustration-adaptation research, also search 画面設計, 画面占有率, 頭身, 身長対比表, 設定画, 三面図, 素体, 作画規格, 基準寸法, 縮尺, 原寸, 原画, 動画, パーツ分け, ドット絵清書, 黄金比, 白銀比, 発注仕様 and 納品形式.

Japanese terms include 制作工程, 制作事例, 作画技法, ドット絵メイキング, 背景制作, 内製ツール, 再現実験, 技術考察, 自作描画エンジン, 自作ツール, 制作備忘録, 同人ゲーム制作日記. Search across CEDiL, CGWORLD, J-STAGE, CiNii, NDL, 技術書典, BOOTH, Hatena, Qiita, Zenn, note, GitHub and appropriate homebrew communities. Record queries and dead ends when they materially affect an inference. A discovery set is not proof of completeness.

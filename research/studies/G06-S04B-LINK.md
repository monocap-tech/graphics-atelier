## Target and comparison
A courier's LINK control refers to a currently selected remote sentinel. A valid request becomes pending immediately; a delayed outcome may succeed, fail, or cancel. The player needs to distinguish *request received* from *link established*, including when the control relocates or sentinel identity changes. Both treatments retain the same persistent explicit status (idle/available, pending, linked, failed, cancelled/unavailable) and separate brief acknowledgment. Baseline B0 immediate textual/state change alone. A attached luminous glint, following the control's local anchor, brief confirmation of request receipt only. B intrinsic border/color/geometry transition on the same control, brief confirmation, preserving its identity instead of adding a graphical entity. Wrong control W world/screen-fixed detached glint replaying at old position or false completion after cancellation. Not all free objects are wrong; W is wrong for this specific host contract. Hold host layout trajectory, actor, status glyph/text, palette family and acknowledgment duration fixed; shapes and affected area differ by design. Report unmatchable luminance, support, visual hierarchy; no claim equal perceptual weight. No detached autonomous phenomenon treated as equivalent without reason.

## Explicit policy, independent of implementation
Use a finite input schedule at local 60 Hz, ticks 0..119. Normal accept t12, relayout t16, success t60; request acknowledgment interval [12,20), pending [12,60), linked [60,120). Cancel variant accept t12, relayout t16, cancel t18, suppress old acknowledgment [18,120); delayed success t60 ignored. Retarget variant accept t12 for sentinel A; at t16 target B selected and old request invalidated; A cue ends immediately, B receives explicit available status, old callback ignored. Retry variant accept t12, failure t40, reaccept t50, success t100, acknowledgment [12,20) and [50,58), pending [12,40),[50,100). Repeat-click while pending ignored; no second acknowledgment or new request. Host removal t16: pending logic may remain for normal case, no orphaned cue while host absent; reappear t30 with pending status and no old acknowledgment. Additional background/occlusion and optional decorative FX toggle variants: underlying state/status unaffected; receipt information itself semantically required, cannot be switched off as mere decoration (B0 and accessible reduced-motion equivalents allowed; the distinct transient mark is required only in A/B under their declared contracts). Freeze exact anchors, trajectories, visible regions, action IDs, event precedence and expected per-tick row table in separate oracle before implementation. Proposed schedules, not source timing. Treat reference and host separately; ensure no stale request ID on rebind.

Truth policies: status is exhaustive for declared available/pending/linked state on visible host; acknowledgment is transient for valid request event, not indication of pending duration or final success. For future counter cue, cue(t) implies valid counter(t), not necessarily converse; define distinct tutorial/full-information policy. Do not apply these rules to atmospheric effects.
